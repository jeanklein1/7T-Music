CC HANDOFF S2 — THE THREE CORRECTIONS
Each one derives its number from the ledger's reference column. Every
formula ships with a worked example (the standing handoff law).

COMMIT [S2a] — the point-source flee: falloff, shell, gains
1. CLASS B — the composed radius drops `personal_radius`. The point's
   social shell IS the bubble; the personal shell is a BODY radius and
   has no business in a presence term:
     let ppr = config.point_bubble_radius;     // 20 wu (was 30+20 = 50)
   Derivation comment: "the point's social shell is the bubble — the
   semantic radius of presence (contracts/point.hpp). personal_radius
   is a BODY shell and was double-counting a body into a presence
   term (CONTACT_4)."
2. CLASS B — add the PROXIMITY FALLOFF, the term the servo never had.
   `behavior_flee` already uses this exact shape (`1 − dist/radius`) —
   cite it:
     let pd   = sqrt(pd2);
     let prox = clamp(1.0 - pd / ppr, 0.0, 1.0);   // full at contact, nil at the shell edge
     let deficit = v_ap * g_self.flee_gain_player * prox
                 - dot(vec2(agent.vel_x, agent.vel_z), pdir);
   Comment: "the flee is a REFLEX, not a policy: nil at the shell edge,
   full at contact. Without this the floor is constant across the whole
   shell and the crowd flees a walking player from a patch away."
3. CLASS B — `AGENT_TIER_GAINS.flee_gain_player` becomes **< 1.0 on
   every row** — the catchability law:
     worker 0.70 · scout 0.85 · sentinel 0.50 · leader 0.60
   Row comment: "CATCHABILITY LAW — the escape is a velocity FLOOR, so
   a gain ≥ 1.0 means the agent matches or beats the player's radial
   speed and can NEVER be approached (nor possessed). Gains < 1 close
   the gap at (1 − gain·radial_share) of player speed. The tangential
   split (esc = normalize(dir + tang·0.6), radial share ≈ 0.86) makes
   the dodge read as evasive at gains well under 1. Jean-tunable;
   keep every row < 1.0."

   WORKED EXAMPLE (commit message): player 15 wu/s, worker at 6 wu
   inside a 20 wu bubble. prox = 1 − 6/20 = 0.70; demand =
   15 · 0.70 · 0.70 = 7.35 wu/s; radial share 0.86 ⇒ the worker recedes
   at ~6.3 wu/s while the player advances at 15 ⇒ the gap closes at
   ~8.7 wu/s: catchable, and the agent visibly darts aside. AT THE EDGE
   (pd = 20): prox = 0 ⇒ no reaction at all. BEFORE: constant demand
   18 wu/s at every distance out to 50 wu ⇒ uncatchable.

COMMIT [S2b] — the cubes: a radius that can reach them
4. CLASS B — `CUBE_PART_RADIUS` is DERIVED, not guessed. From the S0
   preflight's max spawned `orbit_height` H (plus bob amplitude):
     CUBE_PART_RADIUS = H_max + BOB_MAX + 10.0      // 10 wu of lateral reach at the cube's own altitude
   Author the resulting literal with the arithmetic in its derivation
   comment (e.g. "H_max 18 + bob 3 + 10 ⇒ 31.0; lateral reach directly
   under a cube = sqrt(31² − 21²) ≈ 22.8 wu"). If the preflight shows a
   wide tier spread, use the MAX so every tier is reachable, and say so.
5. CLASS B — the falloff uses the same 3D distance the gate uses (K2b's
   planar falloff disagrees with a 3D gate — a cube directly overhead
   would read falloff 1.0 while being 20 wu away):
     let prox = clamp(1.0 - sqrt(pd2) / CUBE_PART_RADIUS, 0.0, 1.0);
   force = min(v_ap * CUBE_PART_GAIN * prox, CUBE_PART_CAP), response
   planar as before.
6. CLASS B — `CONTACT_CUBE_RADIUS` (the shoulder-a-cube contact term)
   keeps its value but gains the honest derivation comment: "reference:
   cube altitude H ≈ <..> wu. At 3.0 + pawn 1.6 = 4.6 this term is
   REACHABLE ONLY for cubes lower than 4.6 wu — i.e. effectively never
   for a floating cube. The parting field (CUBE_PART_RADIUS) is what
   reaches them; direct contact is reserved for low/kited cubes. Named,
   not a bug."
   WORKED EXAMPLE (commit message): player walks directly beneath a
   cube at 18 wu altitude. BEFORE: pd2 = 324 > 64 ⇒ gate dead, zero
   response at any distance. AFTER (R = 31): pd = 18, prox = 0.42,
   force = min(15 · 1.0 · 0.42, 12) = 6.3 ⇒ the cube swings aside and,
   with λ, keeps some of the displacement.

COMMIT [S2c] — the spheres: stop pushing the player
7. CLASS B — DELETE the sphere loop from `update_player_agent`
   entirely (the block commented "spheres push walkers
   (celestial-massive: only self yields)"). Leave the identical loop in
   `update_other_agents` — agents avoiding spheres is wanted; the
   player being shoved by one was never a goal. Comment at the removal
   site: "spheres do not move the point's body (CONTACT_4, Jean's
   ruling). Agents still avoid them — see update_other_agents."
8. CLASS B — in the SURVIVING (agents) sphere loop, replace the
   authored `CONTACT_SPHERE_RADIUS` with the sphere's own per-instance
   body radius, which is already in the struct:
     let r = g_self.contact_radius + fe.body_radius;
   Derivation comment: "reference: the sphere's OWN body
   (fe.body_radius, per-instance). The retired CONTACT_SPHERE_RADIUS
   12.0 was the sphere's INFLUENCE radius — a colour/terrain field
   range, not a physical body — so agents were being pushed from well
   outside the sphere they could see. This closes the deferred
   per-slot-floater-radii item." Tombstone CONTACT_SPHERE_RADIUS if it
   has no other reader (grep; report).
