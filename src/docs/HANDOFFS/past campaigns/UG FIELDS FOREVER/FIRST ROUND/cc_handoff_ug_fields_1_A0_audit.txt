PURPOSE:    two claims in the UG_FIELDS_1 plan are asserted from reading and
            must be measured before the campaign proceeds:
              (1) the campaign adds no bindings and no layout is at its cap

SECTION 1 — DEVICE LIMITS AS ACTUALLY REPORTED
--------------------------------------------------------------------
From the adapter/device setup in state.hpp (or wherever limits are
requested), report the REQUESTED and the DEFAULT value for:

  maxStorageBuffersPerShaderStage
  maxUniformBuffersPerShaderStage
  maxSampledTexturesPerShaderStage
  maxStorageTexturesPerShaderStage
  maxInterStageShaderVariables  (and ...Components if present)
  maxBindGroups

If the code requests raised limits, say which and to what. If it accepts
defaults, say so explicitly — the plan's headroom math depends on which.


SECTION 2 — PER-LAYOUT BINDING CENSUS
--------------------------------------------------------------------
For EVERY bind group layout created in state.hpp, report a row:

  layout name | group | storage buf | uniform buf | sampled tex |
  storage tex | sampler | visibility mask per entry class

Count per SHADER STAGE, not per layout total — a binding visible to both
Vertex and Fragment consumes a slot in each. Where an entry's visibility
is Vertex|Fragment, count it in both columns.

Then a headroom column: limit - used, per stage, per class.

Flag every layout at or within 1 of any cap. CC-6 recorded Render Entity
at 10/10 storage in both VS and FS before the Ground Card landed; confirm
or correct that number now.


SECTION 3 — ZONE BUFFER RESIDENCY (the D small-cut question)
--------------------------------------------------------------------
For each of  zone_config,  zone_life,  zone_life_tex_write,
zone_life_read,  zone_derive_requests:

  a) every bind group layout that declares it
  b) every bind group that binds it
  c) every WGSL entry point whose closure resolves it
  d) which shader stages see it

The specific question: after the Ground Card / D small cut, are the zone
BUFFERS still reaching any render-side layout, or do only the GoL compute
layout and the live-card writer hold them? Answer yes or no, with the
evidence from (a).

This determines whether S3's texture and stride growth is free. If the
buffers still sit in a render layout, say which and at what headroom.


SECTION 4 — THE DIMENSION TWINS
--------------------------------------------------------------------
S3 moves the zone grid from 32 to 64. Every twin must move in lockstep.
Produce the complete list. For each symbol: its declaration site, its
value, and EVERY read site.

  C++ side:   Dim::GOL_ZONE_GRID
              Dim::GOL_ZONE_CELLS
              Dim::GOL_ZONE_LIFE_STRIDE
              Dim::MAX_GOL_ZONES
              PATCH_CELL_SIZE  (the 3.125 the zone grid is snapped to)
  WGSL side:  GOL_ZONE_TEX_N
              GOL_ZONE_STRIDE
              GOL_CELL_VISUAL / VELOCITY / TARGET / NEXT / HEIGHT_FACTOR
                and the remaining plane offsets — list ALL of them with
                their values, and state the plane count
              ZONE_DERIVE_CELL_SIZE

State explicitly whether GOL_ZONE_STRIDE (WGSL) and
Dim::GOL_ZONE_LIFE_STRIDE (C++) are the same number today. If they differ,
that is a finding — report it before anything else.

Report MAX_GOL_ZONES' value and confirm it is <= 32 (the evolve kernel's
tick_mask is a u32 bitfield: `tick_mask & (1u << zone_id)`).

Also report: is any zone_life plane offset written as a literal rather
than derived from the cells-per-zone constant? Each such literal is a
place S3 must touch.
