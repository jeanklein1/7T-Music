WHY
---
zone_life_read is a FIXED 32x32xMAX_GOL_ZONES texture, created from
Dim::GOL_ZONE_GRID in state.hpp. UNIFIED_GROUND_1 U5 made zp.grid_size
tier-derived over {8, 16, 24, 32}, and zone_gol_evolve writes only
texels [0, grid_size)^2 of each 32^2 layer.

The terrain FS normalizes its fetch by the ZONE's grid, not the
TEXTURE's side, which stretches each zone across the whole layer:

    grid 16, cell k  ->  uv = (k + 0.5) / 16  ->  texel ~ 2k + 1

    k in [0, 7]   reads texels 1,3,5..15  = a NEIGHBOUR's colour spring
    k in [8, 15]  reads texels >= 17      = never written -> 0, no tint

The Conway tier table is thirds 32/24/16 and the Pulse table 32/16/8,
so roughly two thirds of zones have their tint scrambled in the near
half and dead in the far half. This is the COLOUR half of "the cells
disappeared" — independent of handoff A, which is the HEIGHT half.

At grid_size = 32 the repair is a no-op (32.0 == f32(32u)), so the
visual evidence at the gate is specifically the smaller-tier zones
coming back.

EDIT 1 of 2 — declare the texture's side beside the geometry it belongs to
--------------------------------------------------------------------
GOL_ZONE_STRIDE already encodes 7 x 1024 = 7 x 32^2. The texture side
is the same fact and belongs in the same block. FIND is ASCII-only and
stops before the trailing comment, so that comment survives untouched.

FIND (exactly 1 occurrence):
const GOL_ZONE_STRIDE: u32 = 7168u;

REPLACE:
// The zone life texture's side — twin of Dim::GOL_ZONE_GRID
// (state.hpp). FIXED at 32 while zp.grid_size is tier-derived over
// {8..32}: the sim writes texels [0, grid_size)² of a 32² layer, so
// every fetch normalizes by THIS, never by the zone's own grid.
const GOL_ZONE_TEX_N: f32 = 32.0;
const GOL_ZONE_STRIDE: u32 = 7168u;

(The original line's trailing "     // floats per zone (7 slots × 1024
cells)" remains attached to the GOL_ZONE_STRIDE line. Confirm it did.)

Forward reference is legal and already load-bearing here: the terrain
FS in §6 reads zone_life_read and zone_params, both declared in §7.0d.
No ordering change required.


EDIT 2 of 2 — the fetch
--------------------------------------------------------------------
FIND (exactly 1 occurrence):
let uv = (vec2<f32>(local_cell) + 0.5) / f32(zp.grid_size);

REPLACE:
let uv = (vec2<f32>(local_cell) + 0.5) / GOL_ZONE_TEX_N;

vec2<f32> / f32 is component-wise in WGSL — no cast, no shape change.

DO NOT touch the neighbouring
    let cell_size = zp.extent / f32(zp.grid_size);
in the same block, nor its twins in contrib_gol_zones_at and
zone_seed_mask. Those correctly divide the zone's WORLD extent by the
zone's OWN grid. Only the TEXTURE fetch was wrong.
