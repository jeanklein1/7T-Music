GIT PROTOCOL — STANDING FOR EVERY PRUNING_1 PASS
───────────────────────────────────────────────────────────────────────
7T runs trunk-based on master. Work on a `claude/pruning-1-*` branch if
you need one, but it is a transient review handoff, never lineage:

  1. Record `git rev-parse HEAD` on master before you start.
  2. Do the work.
  3. MERGE TO MASTER AND PUSH THE SAME DAY. Then delete the branch,
     local and remote.
  4. Report back: the master hash your work landed at, and the branch
     name you deleted.

Do NOT leave the pass sitting on a review branch. Jean reads master and
updates project knowledge from master; a parked branch costs him a
manual merge he should never have to perform. If a pass cannot merge
cleanly, say so in the report and stop — do not park it.

P0 is comment-free and code-free, so the merge is trivially safe.

DELIVERABLE A — tools/pruning_census.py (re-runnable)
───────────────────────────────────────────────────────────────────────
The reason scaffolding accumulated is not weak discipline: the tree has
no instrument that makes scaffolding VISIBLE. Build it once; it becomes
a gate at the head of every future campaign, not an event.

Requirements: stdlib only, runs from repo root, prints the report to
stdout and writes audit/PRUNING_1_CENSUS.md. No third-party deps, no
network. Deterministic output (sort every list) so successive runs diff.

Parsing notes, so you do not over-engineer:
· Strip WGSL comments (`//` to EOL, `/* */`) before any symbol pass.
  WGSL has no string literals to worry about.
· WGSL has NO user-function overloading and names are unique in the
  file, so `\bNAME\s*\(` is a sound call-site test post-strip.
· Entry points: `@compute`, `@vertex`, `@fragment` attributes.
· Build the call graph, then mark reachable from entry points.

§1 — WGSL SYMBOL CENSUS (realization/world.wgsl)
    Per `fn`: name · line · declared? · reachable-from-any-entry? ·
    call-site count · which entry points reach it.
    THEN THE SECOND GATE, which matters more than the first: cross the
    entry-point list against the pipelines actually CREATED in
    realization/renderer.hpp. An entry point with no pipeline is dead,
    and everything reachable only through it is dead with it. Report
    that set separately and loudly.
    Also census: `const` declarations with zero post-strip references;
    `struct` declarations with zero references; `override` declarations.
    Report totals: file lines, comment lines, `fn` count, unreachable
    `fn` count, unreferenced const count.

§2 — BINDING CENSUS
    Three rooms, one table: realization/binding_registry.hpp (the
    authored numbers), realization/state.hpp (layout + group entries),
    realization/world.wgsl (@group/@binding declarations).
    Per slot: (group, binding) · registry constant name · WGSL variable
    name · bound in which bind groups · read by which REACHABLE WGSL
    functions.
    Flag four classes:
      (a) registry constant with no WGSL twin;
      (b) WGSL declaration with no registry constant;
      (c) bound resource read by zero reachable functions  ← GPU cost;
      (d) "reserved / parked / do not reuse" comments — per the ruling
          these are superstition, since the registry IS the single
          source; list them for retirement.
    This section is where the campaign's real GPU savings live. Be
    exhaustive here even if §1 is long.

§3 — CONFIG MIRROR CENSUS (feeds P3 directly)
    Parse `struct GPUDesignConfig` (state.hpp) and `struct DesignConfig`
    (world.wgsl) field by field, in order.
    Emit: index · C++ name/type/offset · WGSL name/type/offset ·
    AGREE/DISAGREE · reader count in C++ · reader count in WGSL ·
    setter name · setter caller count (excluding the boot-pin block).
    Compute BOTH offset columns honestly: C++ packs f32/u32 at align 4;
    WGSL rounds vec3<f32> to align 16. The four vec3 members are where
    the rooms can silently diverge — state.hpp's own comment says so.
    Report every field whose readers are zero in BOTH rooms as a
    deletion candidate with its byte cost, and give the running total.
    Expected (verify, do not assume): wave_time_scale, wave_enable_mask,
    wave_freeze_mask, wave_frozen_t[3], pawn_amp_scale,
    pawn_height_bias, mute_dynamics_2d, active_cell_size.

§7 — THE VERDICT TABLE (the artefact Jean rules from)
    One row per candidate, sorted by tier. Columns:
      symbol | room | file:line | claimed STATUS | reachable callers |
      removal instrument | disclosure | recommended verdict
    `removal instrument` is how P1/P2 would PROVE the removal safe —
    one of: glaw1 (C++ compile) · glaw2 (naga/Tint parse) · Dawn
    enumeration probe (bind the layout without the entry; Dawn objects
    if live) · rest bit-identity · idle rig · none-needed.
    `disclosure` is any visible or behavioural consequence. A pure
    deletion should read "none — behaviour-identical by construction";
    where it does not, say exactly what changes.
    `recommended verdict`: DELETE · KEEP(reason) · RULE(Jean).
    Anything you are less than certain of goes to RULE(Jean). The
    failure direction we want is under-reach, never over-reach.

      · Tree mass: lines and files, which is what a context window pays.
